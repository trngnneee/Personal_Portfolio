F-01

IP rate limiting keyed on transient proxy egress IPs — login/contact throttles bypassable

MediumConfirmed
Target T1 (affects T2 contact form, T3 login) Component rate-limit.ts + trust proxy: 1 CWE-307 / WSTG-ATHN-02 CVSS 5.3 AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L

The login (10/15 min) and contact (5/15 min) limiters bucket per IP as seen by the origin. The request path is client → Cloudflare → Render → Express, but only one proxy hop is trusted, so the key is Cloudflare's rotating shared egress IP. The RateLimit headers prove it: one curl client spread across 4–6 independent buckets in six requests, and an attacker cycling egress IPs can post to /contact far beyond the cap — unbounded owner-paid Resend emails and DB rows. The flip side: two visitors behind one egress IP share the tiny 5-request window. Credential brute-force stays contained by the DB-side account lockout (5 failures → 15 min) — which anyone can also trip against the single admin account on purpose.

Evidence — six requests, same client, distinct bucket keys 
POST /api/v1/admin/auth/login   ×6
< RateLimit: "10-in-15min"; r=5; pk=:ZmIwNDE4YWM4YTE5:
< RateLimit: "10-in-15min"; r=8; pk=:OTA0MTExMmZlNTRh:   ← different bucket, higher remainder
< RateLimit: "10-in-15min"; r=6; pk=:ZjFhOGNhOThiN2U5:   ← a third bucket
# a single per-client bucket would read r=5,4,3,2,1,0
Fix 
// app.ts — behind Cloudflare → Render: trust two hops, or
app.set("trust proxy", 2);
// or in express-rate-limit v8 (unspoofable — Cloudflare rewrites it):
keyGenerator: (req) => req.headers["cf-connecting-ip"] ?? req.ip

Retest: ≥5 rapid POSTs from one client ⇒ single pk, monotonic r; a second client on another exit IP gets its own counter; spoofed X-Forwarded-For cannot steal it.

F-02

CORS allowlist retains suspended, re-claimable portfolio-admin.onrender.com

LowConfirmed
Target T1 configComponent render.yaml → CORS_ORIGINSCWE-942CVSS 2.7 AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:N/A:N

The entry still echoes Access-Control-Allow-Origin live, yet the hostname today serves Render's 503 "Service Suspended" page. *.onrender.com names are globally claimable once released — the API itself collided with one (hence -5hvt). If the old admin service is deleted, any Render customer could run script from an allowlisted origin. Blast radius stays small because auth rides a sessionStorage Bearer token, not ambient cookies. Fix: drop the entry; keep trngnneee.io.vn and admin.trngnneee.io.vn.

F-03

Database TLS encrypted but server-certificate-unverified by default

LowLikely — deployment dependent
Target T1 → Supabase linkComponent db/client.tsCWE-295CVSS 2.4 AV:A/AC:H/PR:N/UI:N/S:U/C:L/I:L/A:N

DATABASE_SSL=true without DATABASE_CA_CERT yields rejectUnauthorized:false (the code warns about exactly this). An on-path adversary could impersonate the pooler. Both hops are provider backbones, so this is defense-in-depth; the optional fix is already wired: paste Supabase's CA PEM into DATABASE_CA_CERT in the Render dashboard. Marked Likely because the secret's actual dashboard value couldn't be inspected externally.

F-04

/healthz reveals DB liveness to anonymous callers

InformationalConfirmed

{"ok":true,"db":"up"} with correct Cache-Control: no-store. Conventional status-endpoint exposure; no versions, paths or timings. Acceptable — listed for completeness.

F-05

Hardening nits: HSTS lacks preload; T2 has no COOP/CORP

InformationalConfirmed

All three send max-age=31536000; includeSubDomains and strict CSP (script-src 'self', frame-ancestors 'none'). Missing preload is optional (review the whole-domain implication of includeSubDomains on io.vn first); COOP/CORP matter little with zero cookies. The /* SPA rewrite returns the HTML shell for unknown /assets/* paths, which confirmedly prevents source-map leakage.

What the system does right

  • ✓Fail-closed admin boundary — requireAuth mounted once before the whole admin router: 14/14 endpoints and unknown paths returned 401 live; no unauthenticated route enumeration.
  • ✓Token design — HS256 pinned (alg-confusion & alg:none rejected live), shape-checked, 8 h TTL, DB token-version revocation (logout-all).
  • ✓Timing-equalized login — argon2id + dummy verify; wrong-email vs wrong-password responses byte-identical; 2/5 probe attempts left lockout margin untouched.
  • ✓Schema-first input layer — zod at every boundary (mass-assignment resistant), digit-only id params, LIKE-wildcard escaping, 1 MB body cap (413 verified), all SQL parameterized.
  • ✓Sanitized output — React escaping + rehype-sanitize markdown + Mermaid strict + XML-escaped RSS + JSON-LD <-escaping; allowlist DTOs strip ipHash/internals; private repo URLs suppressed.
  • ✓No cookie surface — zero Set-Cookie on any target ⇒ CSRF structurally not applicable; CORS exact-origin, no Allow-Credentials.
  • ✓Defense-in-depth — RLS enabled on every table, statement_timeout 10 s, bounded pool, log redaction of auth headers/passwords, salted SHA-256 IP storage, honeypot that stores nothing.
  • ✓Process — CI gates npm audit --omit=dev + lint + typecheck + a dedicated security regression suite mirroring this assessment's checks.

Actions

Priorities

  1. Fix limiter keying (F-01) — one-line change; retest per the monotonic-bucket criterion.
  2. Drop the stale CORS origin (F-02) — one edit in render.yaml.
  3. Set DATABASE_CA_CERT (F-03) in the Render dashboard if unset.
  4. Optionally: authenticated follow-up pass (live token expiry, logout-all, upload rejection, one synthetic CRUD roundtrip) whenever owner credentials are shared — all currently source-verified only.

Limitations of this assessment

  • No privileged session: authenticated write paths and live revocation/expiry are assessed from source + the repository's own security suite, not reproduced against production.
  • Deployed-commit provenance: asset hashes differ from a local build; every probed behavior matches the reviewed source, but exact commit attestation needs the Render deploy log.
  • State touched in production: 2 failed login attempts (lockout counter, resets on next successful sign-in), honeypot-flagged contact POSTs (stored nothing), no uploads, no data mutation.
  • Single-account design ⇒ horizontal-privilege (BOLA) testing not applicable by construction.
